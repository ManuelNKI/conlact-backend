# BE-15 y BE-19 - Entrega de backend de David Barragán

Implementación basada en `CONTRATOS_BACKEND_BE14_A_BE41.md`, proporcionado el 4 de octubre de 2026, y en el esquema real del repositorio. El proyecto conserva Spring Boot 4.1.1 y Java 25 definidos en `pom.xml`; la mención de Spring Boot 3.5 en el contrato es anterior a la configuración actual.

## Seguridad y convenciones

- Base local: `http://localhost:8080`.
- Todas las rutas administrativas requieren `Authorization: Bearer <token>` y perfil `admin` activo en la base utilizada por Spring. El rol se verifica en `profiles`, no se confía en un claim administrativo del cliente.
- UUID reales para productos, variantes y testimonios. Identificadores ilustrativos como `prod-queso-fresco` del contrato no son UUID válidos.
- Los controladores devuelven DTOs y delegan las transacciones a servicios.
- Errores: 400 entrada inválida, 401 autenticación ausente/inválida o perfil inactivo, 403 sin rol ADMIN, 404 recurso inexistente, 409 duplicados/stock insuficiente/conflictos de versión.
- Los errores incluyen `timestamp`, `status`, `error`, `message`, `path` y, cuando corresponde, `validationErrors` (también disponible como `errors`, conforme al manejador existente). Las claves de validación corresponden a los nombres Java de los campos.

### Crear o actualizar

```json
{
  "autor_nombre": "Mercedes Caisabanda",
  "autor_tipo": "Maestra Quesera",
  "frase": "Conservamos nuestra tradición quesera.",
  "avatar_url": "https://example.com/mercedes.webp",
  "calificacion": 5,
  "is_authorized": true,
  "is_published": true
}
```

- `autor_nombre`: obligatorio, máximo 150 caracteres.
- `frase`: obligatoria, máximo 4000 caracteres.
- `autor_tipo`: opcional, máximo 150 caracteres.
- Entradas alternativas: `autor` para `autor_nombre`, `rol` para `autor_tipo`, `comentario` para `frase`, `avatar` para `avatar_url` y `rating` para `calificacion`. La respuesta conserva los nombres originales.
- `avatar_url`: opcional, URL HTTP/HTTPS, máximo 2048; no se descarga desde el backend. Un texto vacío borra el avatar; omitido/null conserva el valor en PUT.
- `calificacion`: opcional, entero de 1 a 5; omitido/null conserva el valor en PUT.
- `is_approved`, `is_featured` e `is_archived` distinguen aprobación administrativa, destacado y archivo. Destacar exige aprobación y que no esté archivado.
- Se eliminan espacios exteriores; un tipo vacío se guarda como null.
- Al crear, ambos estados son false cuando se omiten.
- En PUT son obligatorios nombre y frase; el tipo omitido se limpia. Los estados omitidos conservan su valor.
- Intentar publicar sin autorización devuelve 400, sin guardar cambios.
- Revocar autorización mediante PUT retira la publicación automáticamente, salvo que el mismo cuerpo intente expresamente publicar, en cuyo caso se rechaza.
- Las escrituras existentes bloquean la fila durante la transacción para que publicaciones y cambios de autorización simultáneos no se sobrescriban.

PATCH publicar admite `{"is_published": true}` o `{"is_published": false}`. Esta forma fija un estado y puede repetirse. Sin cuerpo alterna el estado, según el contrato; un cuerpo `{}` es inválido. Se recomienda enviar el estado explícito desde el frontend.

Para conservar el flujo anterior, la publicación administrativa también expresa aprobación cuando `is_approved` no se envía. Aprobación explícita false y publicación true son incompatibles (400). `/aprobar` no recibe cuerpo: aprueba y publica únicamente con consentimiento y sin archivo. `/archivar` retira publicación y destacado, conservando el registro y su aprobación histórica.

`/moderar` recibe uno o más de `is_approved`, `is_featured`, `is_archived`. Rechazar aprobación retira publicación/destacado; desarchivar (`is_archived=false`) no republica automáticamente. Después se puede usar `/aprobar`. Un cuerpo sin ninguno de esos estados devuelve 400. Todas las acciones requieren ADMIN.

### Respuesta pública

```json
  {
    "id": "e0000000-0000-0000-0000-000000000001",
    "autor_nombre": "Mercedes Caisabanda",
    "autor_tipo": "Maestra Quesera",
    "frase": "Conservamos nuestra tradición quesera.",
    "fecha": "2026-10-04T13:00:00Z",
    "avatar_url": "https://example.com/mercedes.webp",
    "calificacion": 5,
    "is_featured": false
  }

```

La consulta aplica conjuntamente `is_authorized=true`, `is_published=true`, `is_approved=true` e `is_archived=false` en el repositorio. Devuelve todos los aprobados visibles; `?destacados=true` añade `is_featured=true` al filtro. Orden: fecha de creación descendente y UUID ascendente para desempatar. Sin resultados devuelve `[]`. `fecha` corresponde a la creación. Las respuestas administrativas añaden los estados internos y `updated_at`.

La ampliación del 6 de octubre usa `supabase/migrations/20261006_extend_testimonials.sql` y su copia idéntica `docker/init/05_extend_testimonials.sql`. Agrega campos sin eliminar datos y marca como aprobados los testimonios que ya estaban autorizados/publicados. En una base local existente ejecutar `./docker/repair-local-db.ps1`; en Supabase aplicar la migración mediante el procedimiento del equipo.

## BE-19: Productos

### Rutas

| Método | Ruta en español | Alias en inglés | Resultado |
| --- | --- | --- | --- |
| GET | `/api/admin/productos` | `/api/admin/products` | 200, listado por nombre/UUID |
| GET | `/api/admin/productos/{id}` | `/api/admin/products/{id}` | 200, detalle |
| POST | `/api/admin/productos` | `/api/admin/products` | 201, crear |
| PUT | `/api/admin/productos/{id}` | `/api/admin/products/{id}` | 200, actualizar |
| DELETE | `/api/admin/productos/{id}` | `/api/admin/products/{id}` | 204, ocultar |

```json
{
  "asociacion_id": "a0000000-0000-0000-0000-000000000001",
  "categoria_id": "c0000000-0000-0000-0000-000000000001",
  "nombre": "Queso Maduro Andino",
  "slug": "queso-maduro-andino",
  "tipo_queso": "Madurado en Cava",
  "descripcion_corta": "Queso madurado 60 días.",
  "descripcion": "Detalle completo del proceso.",
  "origen": "Pilahuín",
  "conservacion": "Refrigeración constante",
  "status": "published",
  "is_featured": true
}
```

- Nombre obligatorio (máximo 150); slug opcional (máximo 160); tipo de queso máximo 150; descripción corta y origen máximo 500; descripción máximo 10000; conservación máximo 2000.
- Estados válidos: `draft`, `published`, `hidden`. Al crear se usa `draft` y `is_featured=false` cuando se omiten.
- Asociación y categoría son opcionales conforme al esquema; los UUID enviados deben existir (404 en caso contrario).
- Si se omite slug al crear, se genera desde el nombre con sufijo si está ocupado. Un slug explícito duplicado produce 409. Se normalizan mayúsculas, acentos, espacios y guiones bajos.
- PUT reemplaza contenido y referencias: campos descriptivos o referencias omitidos/null se limpian. Slug omitido/vacío, estado omitido y destacado omitido conservan los valores existentes. Las variantes e imágenes se conservan.
- DELETE cambia el estado a `hidden`. Conserva producto, variantes, stock, relaciones con recetas y detalle histórico de pedidos. Para volver a publicar se usa PUT con `status=published`.

Las respuestas administrativas contienen los campos anteriores, `id`, nombre de asociación/categoría, `created_at`, `updated_at`, `fotos`, `presentaciones`, `stock`, `precio`, `peso` y `disponible`.

- `presentaciones` incluye activas e inactivas con campos en español compatibles con el contrato de productos, además de versión y umbrales.
- `stock` suma únicamente variantes activas. `disponible` requiere producto publicado y stock activo positivo.
- `precio`/`peso` corresponden a la primera variante activa por peso ascendente y SKU; sin variantes activas son null.
- Las URLs de fotos se resuelven mediante `IStorage.getPublicUrl`. Consultar productos no sube ni descarga archivos.

### Crear una variante

```json
{
  "sku": "AND-MAD-500",
  "presentation_name": "Cuña 500 g",
  "weight_grams": 500,
  "price": 3.25,
  "stock": 20,
  "low_stock_threshold": 5,
  "is_active": true
}
```

SKU obligatorio, máximo 50, letras/números/guiones/guiones bajos; se guarda en mayúsculas y se verifica unicidad sin distinguir mayúsculas. Presentación obligatoria, máximo 100. Precio obligatorio, no negativo, máximo ocho enteros y dos decimales. Peso opcional, positivo. Stock inicial obligatorio y no negativo; umbral no negativo (por defecto 5); actividad true por defecto.

PUT de variante permite modificar SKU, presentación, peso, precio, umbral y actividad. Los campos omitidos conservan su valor. El stock posterior a la creación se cambia mediante las rutas de stock; DELETE no elimina variantes referenciadas por pedidos. `is_active=true` en PUT reactiva una variante.

La creación y la actualización hacen flush antes de construir la respuesta para devolver fechas y versión ya persistidas.

### Operaciones de stock

Descuento/reposición:

```json
{"quantity": 3, "reason": "venta_mostrador", "version": 0}
```

Ajuste:

```json
{"stock": 45, "reason": "toma_fisica_inventario", "version": 1}
```

- `quantity` obligatorio, entero positivo; `stock` obligatorio, entero no negativo. Los decimales y valores fuera del rango integer se rechazan con 400.
- `reason` opcional, máximo 500; se recortan los espacios antes de auditar.
- `version` opcional, no negativa. Si difiere de la versión actual se devuelve 409 sin modificar inventario. Es útil para impedir que un formulario antiguo sobrescriba ajustes recientes.
- Stock insuficiente devuelve 409; reabastecimiento que exceda el rango integer devuelve 400. Ningún caso modifica stock o genera auditoría.
- BE-18 aplica `@Version` al guardar y hacer flush. Una modificación concurrente devuelve 409 y revierte la transacción.
- Cada operación exitosa guarda un evento en `audit_log`: actor autenticado, variante, acción, stock/versión antes y después, diferencia y motivo si se envió. Si falla auditoría, se revierte también el stock.
- Descuento y reposición aplican cada solicitud válida. Ante un fallo de red, consultar el estado antes de reenviar; enviar `version` permite detectar una repetición sobre datos antiguos.

Respuesta: DTO BE-18 con `id`, `product_id`, `sku`, `presentation_name`, `weight_grams`, `price`, `stock`, `low_stock_threshold`, `is_active`, `is_low_stock`, `version`, `created_at`, `updated_at`.

## Estado del arranque local

La base local se reparó el 4 de octubre de 2026, con respaldo previo en `target/local-db-backups`. El fallo era `Schema validation: missing table [association_images]`: la inicialización se interrumpía en `03_storage_buckets.sql` porque el rol `authenticated` y `auth.uid()` se creaban recién en el script `04`. El nuevo `docker/init/00_auth_compat.sql` prepara ambos antes de las políticas de Storage. Se verificó una inicialización completa en un PostgreSQL efímero adicional.

`docker/repair-local-db.ps1` recupera bases ya creadas, sin repetir el modelo base ni las semillas; hace respaldo y omite la migración de imágenes si la tabla ya existe. Se comprobó que una segunda ejecución conserva los registros.

En Windows, arrancar con `docker compose up -d` y `.\start-local.ps1`. El script selecciona JDK 25 entre `JAVA_HOME` y `javac` del PATH, y fija un directorio de sockets dentro de `target` para evitar el fallo del cliente HTTP observado con el directorio temporal del sistema. Si solo encuentra otra versión, configurar `$env:JAVA_HOME` con la carpeta del JDK 25 instalado antes de ejecutar el script. Las credenciales no se modifican. Para administración y archivos sigue siendo necesaria la configuración real de Supabase y un perfil ADMIN activo en la base local.

Arranque verificado con el propio script y el JDK 25.0.4 instalado: Spring inició en el puerto 8080, ambos aliases de testimonios respondieron 200 y el listado administrativo de productos respondió 401 sin token. Se cerró la instancia de verificación después de comprobar las respuestas.

La comprobación del 6 de octubre repitió el arranque con la ampliación de testimonios y el servicio de correo: ambos aliases públicos devolvieron 200 con los 2 registros existentes y los nuevos campos, `?destacados=true` devolvió 200 con `[]`, y la consulta administrativa sin token devolvió 401. La migración local se aplicó con respaldo; se comprobó también una inicialización completa y una segunda ejecución que conserva decisiones de moderación en PostgreSQL efímero. El backend y el contenedor adicional de verificación se cerraron al terminar; PostgreSQL local permanece disponible.
